# Resume Craft v2.1.0 复盘：一个 Local-first Markdown 简历编辑器的工程取舍

做 Resume Craft 的起因并不复杂。

Markdown 很适合开发者维护内容，但到了简历这个场景，最后总会撞上纸张、分页、字体和 PDF；Word 能处理纸张，却经常把时间消耗在对齐和格式上。

所以我给这个项目定了一个边界：

> 不重新发明简历内容本身，只解决“编辑 → 预览 → 检查 → 导出”这条链路。

GitHub：https://github.com/kunlong-luo/resume-craft  
在线体验：https://kunlong-luo.github.io/resume-craft/

## 1. 先定义非目标

有些功能从一开始就决定不做：

- 不做“ATS 包过”；
- 不做服务端简历存储；
- 不做账号体系；
- 暂不做 OCR；
- 不试图保证不同系统像素级一致。

这些限制反而让架构选择更清楚。

## 2. Local-first 到底落在哪里

草稿、设置和多档案主要保存在浏览器 localStorage。

优点是：

- 打开就能编辑；
- 正常使用不需要账号；
- 核心简历内容不用先上传应用后端。

缺点同样明确：

- localStorage 非加密；
- 跨设备同步需要自己导入导出；
- 设备和浏览器账号本身必须被当成敏感环境。

项目支持 PWA，安装后可以作为独立应用使用。

字体使用系统字体栈，例如 PingFang SC、Microsoft YaHei、Source Han Sans，避免再引入第三方字体 CDN。

## 3. 为什么表单和 Markdown 要共存

如果只做 Markdown，产品会天然排除一部分用户。

如果只做表单，又会牺牲开发者最喜欢的直接编辑体验。

所以当前做法是：表单和 Markdown 共享同一份状态，编辑区可以在不同模式之间切换，旁边预览同步更新。

在这个基础上又加了：

- 拖拽重排经历；
- Section Sorter；
- Profile Matrix；
- 多版本 Diff；
- 中英文混排清理。

复杂度比单向渲染高，但使用层面的收益也更明确。

## 4. 国际化不是“把中文翻成英文”

v2.1.0 新增 Target Market：

- US
- Canada
- UK
- Ireland
- China
- International

这里真正影响体验的是：

- A4 / US Letter；
- 日期格式；
- 模板内容；
- Checker 文案；
- 一些市场相关提醒。

当用户仍使用默认值时，市场切换会应用推荐；手动改过之后，用户自己的值优先。

这比简单做一个中英文按钮更接近真实的跨市场简历需求。

## 5. 分页问题：先承认浏览器排版不是印刷引擎

不同操作系统的字体度量不完全一致，这是浏览器方案绕不过去的现实。

因此项目做的是：

1. 用纸张尺寸作为布局基准；
2. 使用系统字体降级链；
3. 实时显示分页边界；
4. 对轻微超页提供 Auto Fit；
5. 最终以 PDF 验收。

Auto Fit 不是魔法，它只是级联微调边距、行高和段距，适合处理轻微溢出。

## 6. ATS：为什么不做一个漂亮的 92 分

因为那很难证明。

目前 ATS 相关功能只给可解释信息：

- JD 关键词覆盖；
- 联系方式；
- 时间线；
- 技术词汇规范；
- PDF 文本层提取质量。

这些信号可以帮助用户检查简历，但不应该包装成“真实 ATS 通过概率”。

## 7. PDF 为什么保留两套实现

### 浏览器打印

正式投递推荐。

优势是通常能保留文本层，可选择、可搜索。

### html2canvas + jsPDF

作为 Quick PDF。

优势是视觉结果更直接，缺点是光栅化，因此不推荐当作 ATS 投递格式。

如果产品只提供一个“下载 PDF”，这两个完全不同的输出很容易被用户混为一谈，所以我宁愿明确区分。

## 8. PDF 导入为什么宁愿保守

PDF.js 在浏览器本地提取文本。

导入前会分析：

- 可提取文字量；
- 邮箱；
- 电话；
- 常见章节；
- 编码噪声。

如果是扫描件、加密 PDF 或没有足够文本层，就直接提示用户换一种输入方式。

宁愿承认不支持，也不要把错误内容整理得“看起来很漂亮”。

## 9. 分享的安全模型

公开链接：

- 数据放在 URL fragment；
- 不作为 query 参数发给托管站点；
- 但拿到完整链接的人仍然能读取。

密码保护链接：

- PBKDF2 派生密钥；
- AES-256-GCM；
- 随机 salt 和 IV；
- 密码本身不进入链接。

安全说明里也明确建议密码和链接分开发。

## 10. 测试和发布

现在 CI 分成：

- TypeScript / strict boundaries；
- ESLint；
- Vitest；
- production build；
- Chromium E2E；
- Firefox / WebKit 关键流程；
- main/nightly 更完整的跨浏览器回归。

发布流程会检查稳定依赖、版本、构建、测试，再生成 zip / tar.gz 和 SHA256SUMS。

这些东西对一个简历工具看起来有点“重”，但 PDF、浏览器兼容和本地数据类产品很容易因为一个小改动出现回归，所以我认为值得。

## 11. 现在反而应该停止继续加功能

v2.1.0 之后，我更想看真实用户在哪一步流失：

访问  
→ 开始编辑  
→ ATS 检查  
→ PDF 导出  
→ 分享

如果大量用户没有开始编辑，问题可能是定位和 onboarding。

如果编辑很多但几乎没人导出，问题可能在产品流程。

如果大家都能顺利导出，那继续增加十个按钮未必有意义。

所以这次推广我最想收集的反馈不是“你还想要什么”，而是：

**哪一步最难用？**
