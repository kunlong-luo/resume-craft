# 我把简历编辑器做成了本地优先：Markdown、A4/Letter、ATS 与 PDF 的取舍

Markdown 写简历很快，但真正让人头疼的往往发生在最后 20%：分页、纸张、跨设备字体、PDF 导出，以及“这个 PDF 到底适不适合投 ATS”。

我做 Resume Craft，并不是因为市场上缺模板，而是想把这些最后一步的问题收进同一个本地优先工作流里。

在线体验：https://kunlong-luo.github.io/resume-craft/  
GitHub：https://github.com/kunlong-luo/resume-craft

## 先说我想解决的 4 个问题

1. 内容只多两行，简历就从 1 页变成 1.1 页；
2. 国内、美国、英国投递时，A4 / US Letter 和日期格式经常要重新处理；
3. Markdown 好编辑，但很多工具的纸张预览和最终 PDF 不够可控；
4. 简历属于敏感数据，不想为了改一份文档先注册账号、上传服务器。

所以 v2.1.0 的核心思路很简单：

> Markdown 做内容源，浏览器负责排版、检查、导入和导出，核心简历数据尽量留在本地。

## 1. Markdown 和表单不是二选一

编辑区可以在结构化表单、Markdown 源码和板块排序之间切换，旁边的简历画布实时更新。

习惯 Markdown 的人可以直接改项目经历；不想碰语法时也可以用表单。经历和技能支持拖拽重排，二级标题板块可以整体调整。

这样做的代价是同步逻辑更复杂，但好处是用户不用在“可视化编辑器”和“源码编辑器”之间来回复制。

## 2. 把纸张当成布局约束，而不是最后打印时再处理

Resume Craft 支持 A4 和 US Letter。

v2.1.0 又加了一层 Target Market：美国、加拿大、英国、爱尔兰、中国、International。

当纸张和日期仍是默认值时，切换目标市场会给出对应推荐；一旦手动改过，用户自己的选择优先保留。

日期目前支持：

- `2026.09`
- `Sep 2026`
- `September 2026`

预览直接按当前纸张显示分页边界。

如果只是轻微超页，还可以用“一键压缩贴合”微调页边距、行高和段落间距，尝试把内容收回来，而不是先逐段手调。

## 3. 字体一致性：尽量减少变量，但不假装完全一致

项目使用系统字体降级链，例如 PingFang SC、Microsoft YaHei、Source Han Sans 等，不从第三方字体 CDN 加载。

这能减少网络字体带来的额外变量，但不同系统、浏览器和本机字体度量仍可能存在差异。

所以我的原则是：

> 预览负责尽量接近，最终投递仍以导出的 PDF 为准。

## 4. ATS 检查只做“可验证”的部分

这里我刻意没有做“ATS 通过率”这种承诺。

目前主要检查两类东西：

- 粘贴 JD 后，查看关键词覆盖和缺口；
- 检查联系方式、经历时间、技术词汇大小写等常见问题。

PDF 导入也在浏览器里完成。带文本层的 PDF 使用 PDF.js 提取文字，并显示提取质量、邮箱/电话和常见章节识别结果。

扫描件 / 图片型 PDF 暂不做 OCR；带密码或没有可用文本层的 PDF 会直接提示换一种导入方式。

## 5. PDF 导出为什么保留两条路径

**ATS PDF**

走浏览器原生打印 / Save as PDF。

优点是通常能保留可选择、可搜索文本，更适合正式投递。

**快速 PDF**

使用 html2canvas + jsPDF 光栅化页面。

优点是视觉输出直接，适合临时分享或打印能力受限时兜底；缺点是本质上更接近图片，不建议拿它作为 ATS 投递首选。

我宁愿把这两条路径明确区分，也不想用一个“下载 PDF”按钮让用户误以为两者效果完全一样。

## 6. 本地优先不等于“天然安全”

草稿和设置主要保存在浏览器 localStorage 中，它并不是加密保险箱。

项目本身没有用于保存简历内容的应用后端，但你仍然应该把设备、浏览器账号和本地备份当成敏感环境。

分享也分两种：

- 公开链接：载荷在 URL fragment 中，拿到完整链接的人可以读取；
- 密码保护链接：在浏览器本地使用 AES-256-GCM 加密，密码不进入链接。

## 如果你想帮我测，最好不要先看 README

我更想知道的是第一次打开时：

1. 你能不能在 30 秒内理解怎么编辑；
2. 切换 Target Market 后，纸张和日期是否符合预期；
3. 导出的 PDF 是否和预览一致；
4. ATS 提示有没有帮助，还是反而干扰。
