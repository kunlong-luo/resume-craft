# 程序员写简历，用 Markdown 还是 Word？我最后做了一个两者兼顾的方案

先说我的结论：

**如果公司明确要求 .docx，就用 Word；如果你是开发者、需要频繁维护多份简历，Markdown 往往更舒服。**

但真正的问题其实不是 Markdown 和 Word 谁更高级，而是：

> 写完之后，谁来帮你处理分页、纸张、跨设备字体和 PDF 导出？

这也是我后来做 Resume Craft 的原因。

在线体验：https://kunlong-luo.github.io/resume-craft/  
GitHub：https://github.com/kunlong-luo/resume-craft

## Markdown 的优势很明显，但短板也很现实

对开发者来说，Markdown 有几个天然优势：

- 文本结构清晰；
- 复制粘贴不容易把格式带乱；
- Git / Diff 友好；
- 做多个岗位版本时更容易维护。

但一进入“正式投递”阶段，问题就来了：

- 内容多一点，突然变成 1.1 页；
- 国内版本用 A4，美国版本常见 US Letter；
- 日期到底写 `2026.09`、`Sep 2026` 还是 `September 2026`；
- 有些 PDF 看起来正常，文字却不能选择；
- 有些在线工具为了方便，要求先上传简历。

所以我的想法不是“用 Markdown 干掉 Word”，而是让 Markdown 负责内容，让工具接住纸张和导出。

## 我最后采用的是“表单 + Markdown + 实时预览”

Resume Craft 的编辑区可以在表单和 Markdown 源码之间切换，状态与预览同步。

不熟悉 Markdown 时用表单；需要快速改项目经历时直接改源码。

经历可以拖拽排序，板块也能整体调整。

对我来说，这比强迫所有人学 Markdown，或者完全锁在可视化表单里，都更实际。

## 海外简历最大的麻烦之一，其实是“默认习惯不同”

v2.1.0 增加了 Target Market：

- 美国
- 加拿大
- 英国
- 爱尔兰
- 中国
- International

它不会强制替你改简历。

只有当纸张和日期仍然是默认值时，市场设置才会提供对应推荐；你手动改过之后，自己的选择会保留。

目前纸张支持 A4 / US Letter，日期支持 `2026.09`、`Sep 2026`、`September 2026`。

不同公司当然可能有自己的要求，所以这个功能更像“合理默认值”，不是规则裁判。

## ATS 这件事，我反而不想说得太神

很多简历产品喜欢给一个很精确的“ATS 分数”。

我没有这么做。

Resume Craft 现在更关注几个能解释清楚的信号：

- JD 关键词覆盖；
- 联系方式是否缺失；
- 经历时间是否有明显问题；
- 技术名词大小写是否规范；
- PDF 文本是否能被提取。

这些东西能帮助你检查简历，但不能代表某个真实 ATS 一定通过。

正式投递时，我更推荐浏览器打印生成的 ATS PDF，因为它通常能保留可选择、可搜索文本。

快速 PDF 则更适合预览和分享。

## “本地优先”也不是一句营销词

编辑中的草稿主要保存在浏览器 localStorage。

项目没有用于保存简历内容的应用后端，正常使用也不需要注册账号。

但我也会明确提醒：

**localStorage 本身没有加密。**

所以本地优先意味着“减少不必要的数据上传”，不代表你的电脑和浏览器天然安全。

分享链接也做了区分：

- 公开分享：拿到完整链接的人可以读取；
- 密码保护分享：浏览器本地 AES-256-GCM 加密，密码不写进链接。

## 所以，Markdown 还是 Word？

我的答案是：

- 一次性改简历、需要和 HR 交换 .docx：Word 很合理；
- 技术人员、经常维护、需要多个岗位版本：Markdown 很有优势；
- 真正好用的方案，不应该要求你为了排版牺牲编辑效率。

我现在更想验证的是产品本身，而不是继续堆功能。
